# Emerick architecture

Emerick is a small native DAW in C++23 and Qt 6.11 QML, built to be driven by a person and by an agent through the same actions. The core records and plays audio and MIDI on tracks of clips. Everything specific to an instrument or a workflow is a plugin.

## Layers

Each layer is one CMake target. A layer only depends on the layers above it in this list.

| Target | Qt | Owns |
|---|---|---|
| `emerick_core` | no | units and time (frames, ticks at 960 PPQ, tempo map, positions), strong ids, SPSC queues, fuzzy matcher |
| `emerick_model` | no | the project document: tracks, clips, track I/O, plugin track data, undo commands, JSON load and save |
| `emerick_engine` | no | audio and MIDI backends, transport, playback graph, recording to disk, MIDI capture, offline render and export |
| `emerick_view_data` | yes | what the views read and draw from the document alone: track rows, automation params, peak files, waveforms, notes |
| `emerick_app` | yes | the registry, document and engine controllers, QML models, navigation and reveal, introspection, MCP server, Lua host, settings |
| `emerick_ui` | yes | the QML module `Emerick.Ui`: theme tokens and every view |
| `emerick_viewer` | yes | the read-only viewer: the tracks view over a project.json, with the rendered mix moving its playhead |
| `emerick_gm` | no | the General MIDI CLAP instrument the app ships, built on FluidSynth |
| `emerick_voices` | no | the Expansion Voices CLAP instrument the app ships, a sampler for Yamaha expansion pack voices |
| `emerick_arranger` | no | the Yamaha style arranger engine, and the Arranger CLAP device the app ships on it |
| `plugins/*` | both | one folder per plugin; pure C++ parts in their own target with tests |
| `emerick` | yes | the executable: parses flags, wires backends, loads plugins |

The engine never sees the model. `emerick_app` turns the document into an engine `Session` (plain structs) and publishes it to the audio thread. This keeps the engine testable with no project, and the model testable with no audio.

## Single source of truth

- **Document.** All project state lives in `model::Document`. Views, MCP and Lua read it through `emerick_app`; every change is a `model::Command`, so undo, autosave and change notifications have one path.
- **Registry.** Every action, setting, track type, MIDI device profile and plugin QML component is registered once in `app::Registry`. Menus, shortcuts, the Cmd+K palette, MCP tools and Lua all read the registry. A control's QML `objectName` is its registry id.
- **Gestures.** A drag runs its registry actions live through `Registry::updateGesture`, at most once a frame. Each run reverts the last one first, so every view and the engine follow the drag, and `endGesture` leaves one undo step and one action log line with the final values. Escape cancels a drag and reverts it.
- **Notes.** A MIDI clip keeps each note (id, pitch, velocity, start, length, channel) in its notes and every other message in its events. Playback, export and the piano roll read the notes; the engine session gets them as note-ons and note-offs merged with the events, and a recorded take becomes notes when it lands. A looped clip keeps its content once with a loop length, and the session gets every repeat written out.
- **Automation.** A track keeps one lane of points per parameter id (`gain`, `pan`, `mute`, `send.<busId>.level`) and an automation mode. The app resolves each id to an engine target, and the engine evaluates the lanes every 32 samples and ramps the track's gain, pan and sends between those values.
- **Locations.** Each registry entry can name a UI location (`settings.audio.bufferSize`). Revealing a location changes the `Nav` state object only; QML binds to `Nav`, so the same call works for a click, the palette, an agent and a test.

## Projects

- A project is a bundle: a folder named `<Name>.erk` holding `project.json` and `audio/`. On macOS the app's Info.plist declares it a document package, so Finder shows it as one file and opens it in Emerick.
- A new project starts as `Untitled N.erk` in the `Emerick` folder of the platform music folder, so every take lands in a real folder. Autosave writes `project.json` about 2 s after the last edit or take. Leaving an untitled project that holds nothing deletes it.
- The document holds absolute paths in the state of the plugins the app ships (the Arranger style, the General MIDI SoundFont, the Expansion Voices folder). `project.json` holds a path inside the folder the bundle sits in relative to the bundle, which may start with `../`, so a project moved with its files still finds them; other paths and other plugins' state stay as they are. `project.collectFiles`, or `project.save` with `collect`, copies every file the project names from outside its bundle into it, audio into `audio/` and the rest into `files/`, and points the project at the copies as one undo step.
- `video.render` renders the mix as `export.mix` does, then draws `VideoFrame.qml` (the transport counter over the tracks area) offscreen, through the RHI into a texture on a desktop and with the software renderer on the offscreen platform, at each frame's position from the tempo map, and pipes the frames with the mix into `ffmpeg` for an H.264 and AAC MP4. It sets the playhead with `ProjectController::setDisplayPosition` and gives the shared `Nav` view back afterwards. With no window it creates its QML engine on first use.
- Opening a project checks it for missing audio files, clips that run past their file, audio files at another sample rate than the engine's and routes to missing devices, and offers the issues it finds. `project.health` runs the same check and lists them.
- An action that takes a path, such as `project.open` or `export.logic`, opens a file dialog when the UI runs it without one. An agent passes the path, and a missing one is an error naming the param. An action that deletes files asks first in the UI; an agent passes `confirm: true`.
- `export.logic` writes `<Name> for Logic/`: one numbered WAV per audio track from bar 1 to the project end, and `MIDI.mid` with the tempo, the meter, one named track per MIDI track, the project's markers, and markers from the track types that name the timeline, such as chords and Style sections.

## Engine threading

1. The UI thread builds an immutable `Session` snapshot once per event loop turn that changed the project, and swaps it in by atomic pointer at the next block. Retired snapshots return to the UI thread for deletion.
2. Live changes (mute, arm, transport) go through an SPSC command queue drained at block start.
3. The audio callback runs the graph single threaded; a worker pool joins later behind the same interface when profiling needs it.
4. Armed audio tracks write into per-track rings; a writer thread writes the files. Clip playback reads ahead on a reader thread. The writer thread also keeps each take in progress (its frames, peaks and MIDI so far), which the app polls to draw the take while it records. An audio take skips the round trip latency the devices report, so it lines up with what the player heard, and each track's record delay moves its takes later or earlier on top of that.
5. MIDI arrives with absolute timestamps on the MIDI thread, goes through an SPSC queue, and is placed on the timeline in the callback.
6. The audio thread never allocates, locks or frees.

## Metronome

The engine plays the metronome on the tempo map's beat grid to the sample: a synthesized click, the user's samples, or a drum groove synthesized from kick, snare and hat voices, or it sends the same hits as MIDI notes. Its settings live in the registry's Metronome section, and the controller copies them into the session it publishes. A count-in holds the transport at the record position until its bars end, so the take starts there. Takes record only inputs, and exports build their sessions without the metronome.

## Cycle

The document keeps one cycle region and its on flag, which the ruler's upper half, the transport button and C edit. While the cycle is on and playback crosses its end, the engine jumps to its start inside the block, to the sample: it sends Stop to the clock ports, releases held notes, sends the track types' chase at the start, chases MIDI and sends Start, so a device that ignores Song Position Pointer starts over there. Audio clips play the cycle start from a preload the snapshot builder reads, while their streams read ahead again. Recording plays straight through the end. When an audible track aligns playback, as the Style track does, the cycle starts where that track aligns it, and the transport's start reason says why.

## Inserts

The engine scales each track's mix by its trim, ramped over a block when it changes, and then plays its insert effects before the fader. The snapshot builder makes an effect's state once per insert id at the stream's sample rate, with its delay lines at full length, and later snapshots share it, so an edit keeps reverb tails and delay lines and the params glide to their new values. Exports play the effects through the same engine. The limiter delays its track by about 1.6 ms, its 1.5 ms lookahead plus half its interpolation filter, and the other effects add no delay. Each track adds up the delay of its instrument and its inserts that are not bypassed, and the engine delays every other track by what it lacks to the slowest one, with a delay line the snapshot builder allocates, so every track reaches its outputs, its sends and its bus in line; the stream state shows that delay as `pluginDelayFrames` and `pluginDelayMs`. A bus's own inserts stay uncompensated, so a delaying insert on a bus plays its bus late. The limiter estimates each sample's true peak with the 4x interpolation of the loudness analysis, holds the gain each peak needs across the lookahead, releases it slowly and averages it over the lookahead, so the gain is down before the delayed peak plays. `export.mix` with a loudness target measures the integrated loudness of the rendered mix, turns it to the target and runs the same limiter offline for the true peak ceiling, a few passes until it lands within 0.05 LU. A param's id is `<insert id>.<param id>`: an automation lane plays it, and `insert.setParam` takes it in place of the insert param.

## Devices

Each track names its own audio input and output (device id plus channels) and MIDI input and output (port id plus channel). The engine opens the devices that track outputs and the metronome route to, and the inputs of armed and monitored tracks only. It opens them while the transport runs or a track listens live (armed, monitored or with a MIDI input), and closes them once stopped, so other apps keep their devices undisturbed. A route to a device that is gone or cannot run at the engine's rate is dropped and reported, and the other routes still play. With no audio route at all, the engine runs on the default output device at the rate and buffer size it already has. On macOS several devices become one hidden private aggregate device with drift compensation, so the user never builds one by hand. On Linux the devices are PipeWire or JACK ports. On Windows each WASAPI device runs its own stream and the engine resamples the others to the clock device.

Listing devices asks CoreAudio and CoreMIDI about every device, so the engine lists them once at startup and keeps the list. It lists them again when the system reports a device appearing or going away, and on `devices.refresh`. A device that cannot run at the engine's sample rate is refused with the rate to set.

## Plugins

A plugin calls `registerWith(Registry&, ProjectController&, Nav&)` and can add track types (data schema, QML header and lane, engine MIDI processor), actions (listed in the menu bar under `Plugins/<plugin name>`), settings and their settings section (listed under the Plugins heading), MIDI device profiles (channel names, icons), warnings for any track, project-level data in `Document::pluginData` and a QML module. A lane component gets `trackId`, `trackData` and `pixelsPerTick` from the tracks area. The first plugin, `plugins/yamaha`, adds the Chords and Style tracks, the arranger setup and the voice table for Yamaha arranger keyboards. Plugins are compiled in; dynamic loading waits for a third-party plugin.

## Plugins

Emerick hosts CLAP plugins through its own host on clap-helpers, and VST3 plugins through the hosting parts of the Steinberg VST3 SDK. Both formats play behind one `engine::Plugin` interface, with `ClapPlugin` and `Vst3Plugin` behind it. `emerick-plugin-scanner`, beside the app, loads one bundle and prints its plugins as JSON; a VST3 bundle with a `moduleinfo.json` is described from that file without loading. The app runs it once per bundle in the standard CLAP and VST3 folders, `CLAP_PATH` and the `plugins.clapFolders` and `plugins.vst3Folders` settings, and keeps the results in `plugins.json` in the cache folder, keyed by bundle path and modification time. A bundle that crashes, hangs or fails to load stays blocked until it changes or `plugins.rescan` runs. `plugins.list` lists the plugins with their format and whether each is an instrument or an effect, and the blocked bundles.

A VST3 plugin's component and controller are one object or two that we connect. We activate its main audio buses in stereo, or as the plugin keeps them, and hand it param changes and notes through fixed lists, so the audio thread never allocates. A stepped VST3 param counts its steps from 0 and any other param takes the plugin's plain value. Its state in a slot is one blob with the component's state and the controller's. Values the processor changes itself reach the controller on the next idle of the main thread, so its editor and the inspector show them.

A plugin insert holds a plugin slot with its format, id, bundle, name and state, and plays in its track's chain in order with the built-in effects; a bypassed one passes the audio through. `insert.addPlugin` adds one, and `insert.add` does too when it gets a plugin id, with an optional format. Its params go by name: `insert.params` lists them with their values and choices, `insert.setParam` takes a name, exact or else the only case-insensitive match, and a number or a choice's text, and saves the state the plugin then holds into the slot as one undo step, and an automation lane `<insert id>.<param name>` moves a number or on and off param once per block. A plugin's reported latency counts toward its track's delay, which the engine compensates as it does the limiter's. `insert.openPluginWindow` opens a plugin insert's own editor in the same kind of window an instrument's editor gets, and `insert.closePluginWindow` closes it. The window takes the size the editor asks for, follows its later requests, and when the editor resizes, a window the user resizes hands the editor the size it can take. An editor that does not open leaves an error and the insert playing. Each gesture in a plugin's own editor, an instrument's as well as an insert's, from its first touch to its release, becomes one undo step that holds the plugin's new state, and an undo loads the old state into the same plugin, so its window stays open. The insert picker lists the effects of both formats under Plugins. A VST3 instrument takes notes with their velocity and note off velocity as events, and controllers, pitch bend, channel pressure and program change as sample-accurate changes of the params its MIDI mapping names, which we read for every channel when it activates; the notes it sends from its event output reach other tracks as a CLAP instrument's do.

An engine track can play its MIDI through a `Plugin`: its clips, chase, note releases and panic go to the plugin as they go to a MIDI output, and live input reaches it while the track is armed or monitored. The plugin's main output mixes into the track before its inserts, so gain, pan, sends and meters work as on an audio track. The UI thread creates, activates, saves and destroys the plugin. The audio thread queues its MIDI into a fixed buffer and calls process. Whoever holds the instrument's audio guard acts as the plugin's audio thread, so the UI thread can stop processing and reactivate the plugin at a new rate or on `request_restart` while the audio thread skips that block. `request_callback` and `mark_dirty` only set flags that the UI thread reads.

A sysex in a clip, or from live input the track claims sysex from, reaches a plugin whose note input takes MIDI; its bytes sit in a fixed pool through the process call. A plugin's note output feeds other tracks: a MIDI input can name another track as its source in place of a port, and then takes the notes, MIDI and sysex that track's instrument sends, on the input's channel, so the track passes them thru and records them as live input, and its instrument plays them armed or not, as it plays a clip. A sysex from a source reaches the tracks that take all its channels. The engine plays each instrument after the track it takes MIDI from, so the MIDI reaches it in the same block, and drops a loop of these routes.

A MIDI track has an optional `instrument` slot that names a CLAP or VST3 plugin by format, id and bundle path, with its saved state. Without one the track plays to its MIDI output only; with one it also has an audio output, fader, pan, meters, inserts and sends. `instrument.load` and `instrument.remove` fill and clear the slot, and `track.addInstrument` adds a MIDI track with the plugin loaded. A format 10 project that names such a track's kind `instrument` loads it as a MIDI track. The app keeps one live instrument per slot while the slot names the same plugin, attaches it to the session it publishes, and writes each instrument's current state into the slot, as base64, whenever it saves the project; a plugin that marks its state dirty schedules an autosave. A slot whose plugin does not load keeps its state, and the track shows why in its warning badge. `instrument.showEditor` opens the plugin's own floating window, or embeds its editor in a window Emerick creates. `instrument.params` lists the plugin's params with their values and the label of each step of a stepped param, read through its value to text. `instrument.setParam` takes a number or the text of a stepped param's choice, the exact match or else the only case-insensitive one, and names up to three close choices when the text picks none, queues the value for the next process call, or flushes it while the plugin is not processing, waits until the plugin has it and writes the state the plugin then saves into the slot, as one undo step. `voices.audition` renders notes through a fresh instance of the track's instrument with one stepped param set to a voice, on the calling thread, and returns each note's peak, active RMS, spectral centroid and harmonic share, the energy near multiples of the note's pitch over all energy; the track and the document stay as they are. A param whose CLAP module is `Channel <n>` sets what channel n plays, and `instrument.params` reports that channel; the audition renders such a param on its channel, channel 10 for the General MIDI Drum kit, and any other on channel 1, with the params of other channels at their defaults. The engine plays such a render once into the track's mix before its inserts, and keeps the stream open until it ends. A slot whose state changes, as on undo, loads it into the live plugin, and an empty state starts a new instance with the plugin's defaults.

The app ships its own CLAP bundles in `Contents/PlugIns` on macOS and in `clap/` beside the executable elsewhere, and every scan searches that folder first. `src/gm` builds the first one, General MIDI (`org.emerick.gm`): it plays all 16 channels through FluidSynth, with notes, program changes, bank select, controllers, pressure and pitch bend, and channel 10 plays drums. Its params are Sound, the 128 General MIDI sounds, which it sends as a program change to every channel but 10, and Drum kit, the GS kits GeneralUser GS holds, which it sends to channel 10, and Play drums on every channel, which makes every channel a drum channel; Drum kit and Play drums on every channel carry the module `Channel 10`; a program change in the MIDI still picks another sound. Its CLAP state is JSON with the SoundFont path, the sound and the drum kit, and it reads a state that is no JSON object as a plain SoundFont path, as older projects saved it. An empty path plays GeneralUser GS, which the build downloads at a pinned hash and puts with its license in the bundle's `Resources`. A new General MIDI instrument takes the `plugins.generalMidiSoundFont` setting as its state.

`src/voices` builds Expansion Voices (`org.emerick.voices`), which plays the voices of the Yamaha expansion packs installed in Yamaha Expansion Manager, read from its store folder: each pack's UVF voice files and the wave blobs the packs share. It lists the voices whose waves all decode, as 16-bit linear audio or as WXC1 compressed audio. A note plays every zone whose element and key bank cover its note and velocity, at the zone's sample rate, pitched from its center note with its coarse and fine tune in semitones and cents, and looped over the wave's sustain loop unless the zone is a one-shot. The host's main thread reads the store, and decodes a voice's waves when the voice is picked; the audio thread plays them. Its params are Voice, a choice of "Pack / Voice", Volume, Tune, Attack, Release, and Follow program changes, which lets bank select and program change pick the voice at that address, or none when the store holds no such voice. A hidden read-only param names the notes of the picked voice whose WXC1 waves decode with noise, where more than one sample in 200 overflows full scale, and the track shows it as its warning. Its CLAP state is JSON with the store folder, the voice by pack, name and address, and the other params; a voice with no pack and name is picked by its address. An empty state folder reads the folder in the `EMERICK_VOICES_FOLDER` environment variable, which the app sets from the Expansion Voices folder setting (`yamaha.voicesFolder`) and which makes every such instance read the store again when it changes, else Expansion Manager's own folder on macOS.

The host hands each instrument its transport every block: playing, the song position and the cycle in quarter notes, the tempo and the meter. `src/arranger` builds Arranger (`org.emerick.arranger`), a note effect with no audio. On a Style track it reads the chord sysex and the section buttons the track sends for the keyboard, plays the loaded style on them as the transport plays, and sends the eight parts on channels 9 to 16 from its note output, with each part's bank, program, volume and pan when a style loads and on every start. A Style track with an instrument also sends it the first Chords track's chords, and its chase at a play, a locate or a cycle jump reaches the instrument too, so when playback jumps the Arranger starts over at the bar line with the section and the chord that apply there. Its param is Auto fill, and its CLAP state is JSON with the style file's path, the FNV-1a hash of its bytes, Auto fill, and the style's bytes in base64 up to 2 MB, so `project.json` alone plays the style; a state without the bytes plays the file at the path. `arranger.setup` adds the Chords and Style tracks a project lacks, loads Arranger on the Style track and adds a track per part that takes the Arranger's output on its channel, through Expansion Voices with Follow program changes on when it holds the part's voice, else General MIDI. `arranger.style.list` lists the styles in the Style folders setting. `arranger.style.notes` lists, per section and part of the loaded style, the part's voice and how often each note starts in the pattern before any chord transposes it, with each drum key's General MIDI note and name through the voice list.

## Agent interface

The app serves MCP over streamable HTTP on loopback (`--mcp-port`). Tools: `ui.tree`, `ui.find`, `ui.reveal`, `ui.invoke`, `ui.set`, `actions.list`, `actions.run`, `actions.batch`, `settings.get`, `settings.set`, `state.get`, `lua.eval`, `console.log`, `screenshot`. Every tool returns the state after the change. An action that fails leaves the document and its undo history as they were. `actions.batch` and `emerick.batch` run up to 1000 calls, each as its own undo step. With `--agent-read-root` and `--agent-write-root`, every path an MCP or Lua request names goes through one check that resolves symlinks and `..` and refuses a path outside the root; paths from the person using the UI stay open. `--lua-timeout-ms` stops a Lua run after that much wall time outside `emerick.wait`, `--lua-memory-mb` caps what Lua holds (256 MB by default), `--max-render-seconds` refuses longer offline renders before they start, `--bundled-plugins-only` scans and loads only the plugins the app ships, and the `limits` state lists them. Lua (5.4 through sol2) sees the same document and registry, and its `ui` functions and the `ui.*` tools both go through `UiApi`, so a script and an agent can do anything a click can. A plugin reports the tracks whose instruments still load their sounds through the registry, as the Yamaha plugin does for Expansion Voices reading its store; `project.summary` reads them as `ready`, and `project.waitReady` returns once none loads. `track.analyze` and `tracks.analyze` with a resolution measure each bar, beat or step of seconds, and `mix.inspect` renders the mix and every audio track and bus once and lists what a listener would hear as wrong (whine, beep, clipping, DC offset, imbalance, silence, harshness) by track and bar, so an agent can check a render without listening.

## Console and scripts

The console (Cmd+\`) runs Lua in the same sandboxed host on the UI thread. `Registry::run` emits `actionRan` for every action a person, the palette, MCP or Lua asked for, and the console writes each one to its action log as the Lua call that runs it. Lua files in the user scripts folder and in `<bundle>/scripts` become actions in the Scripts menu; a header comment names their title, shortcut and description. tree-sitter parses the Lua the console shows, for its syntax colors.

## Testing

- Catch2 unit tests per target. The engine runs on `OfflineBackend`, faster than realtime, with golden renders.
- `NullAudioBackend` and an in-process virtual MIDI port, selected with `--audio=null --midi=virtual`, let the app run anywhere. With the virtual port, `midi.inject` feeds it and `midi.sent` lists what the app sent to it.
- `docker/` builds the `release` preset with its tests in Ubuntu 24.04 with Qt 6.11 and copies the app, the Qt libraries it links and its CLAP bundles into a slim runtime image. The image runs the session service by default, or one headless app (`QT_QPA_PLATFORM=offscreen`) with `app`, and `e2e/` drives both over MCP.
- CI runs `make quality` on macOS and Ubuntu, `make service-check` and `make e2e` on every pull request and push to main. After they pass on a push to main, a `v*.*.*` tag or a published release, CI publishes the image for amd64 and arm64 to GHCR. An action test fails when a registry action has no menu entry, shortcut or control.

## Session service

`service/` is a Python service (FastAPI, SQLite) that turns the single-user headless app into one MCP server per session. It keeps projects and sessions in SQLite, starts one `--headless` app per session on a loopback port with its agent roots set to the project folder and resource limits on the process, proxies `/sessions/{id}/mcp` to it, and saves and stops sessions that idle, run too long or outgrow their disk quota. Projects live in a local folder or in S3, which a session checks out into its work folder and stores back on save and close. `docs/service-security.md` lists the limits it applies.

## Viewer

`src/viewer` builds a read-only viewer from the app's own QML views. `ViewerProject`, `ViewerTracks` and `ViewerRegistry` take the place of the Project, Tracks and Registry singletons and fill them from a project.json through the row builders in `emerick_view_data`, which `TrackListModel` uses too. The registry reports `readOnly`, so the views hide every edit, and it runs only the actions that look around a project (play, pause, stop, move the playhead, zoom, show automation lanes) with the titles and keys the app gives them in `view_actions.hpp`. The viewer shows the app's transport bar and display above the tracks, opens the automation of a project that has lanes, and opens the app's piano roll on a double-clicked MIDI clip and the mixer, both read-only. Waveforms come from the bundle's `.peaks` files, which `project.writePeaks` writes and the viewer fetches over HTTP. `make viewer-wasm` builds it with Qt for WebAssembly 6.11.3 and emsdk 4.0.7 into `build/viewer-wasm/site`, and the image ships those files in `/opt/emerick/viewer`. The page reads `project`, `mix` and `bundle` URLs from its query, waits while the service answers 202 for the mix, plays the mix in a hidden `<audio>` element and moves the playhead with it.
